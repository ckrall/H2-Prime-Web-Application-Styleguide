Section 09 — Framework Implementation

9A

Tailwind CSS v4

main.css is the Tailwind v4 entry point. It imports Tailwind itself, imports components.css, and then declares an @theme block that re-exposes every Tier 2/3 token from tokens.css as a Tailwind design token — which is what turns --color-surface-page into the real utility class bg-surface-page.

9A-1Download the source files

The three files below are the actual runtime source — not excerpts. Pull them directly into a project rather than hand-copying from this page.

tokens.css
Authoritative token source. All three tiers — primitives, semantics, dark mode, dashboard themes, phase context, and the shadcn/Radix bridge (§9B). Framework-agnostic.
Download tokens.css
main.css
Tailwind v4 entry point. Imports Tailwind and components.css, then maps every token into the @theme block covered below.
Download main.css
components.css
Tier 3 base layer. Applies semantic type roles to real HTML elements inside a Tailwind @layer base block — see Section 8 §8E.
Download components.css
Load order still applies
Downloading these individually doesn't change how they're wired together — tokens.css loads first, main.css imports Tailwind plus components.css second, per §8E. Drop all three into the same directory as your project's global stylesheet import.

Each Tailwind prefix maps to a fixed utility family, so a single @theme entry generates several related classes at once:

Resulting usage in markup
Theme switching resolves through the variable chain, not new classes
Applying [data-theme="filer"] or [data-theme="admin"] to a layout root doesn't require different Tailwind classes per dashboard. bg-interactive-primary always compiles to the same utility; what changes is which value --interactive-primary-bg resolves to underneath, per the dashboard theme layer in tokens.css §4.
9B

shadcn/ui — the variable contract

shadcn/ui isn't an installed component library in the traditional npm-dependency sense — it's a collection of accessible, Radix-based component source files that get copied directly into a project and then owned and edited locally. Its components are styled entirely through a fixed, well-known set of CSS variable names (--background, --primary, --destructive, --ring, and so on), which means any design system can make shadcn's components match its brand purely by defining those variables — no fork of the component source required.

tokens.css §6 is exactly that: a one-time bridge mapping every variable shadcn's components expect onto the H2 Prime semantic token that already carries the right meaning.

shadcn variableH2 Prime token
--background→--surface-page
--foreground→--text-primary
--card→--surface-raised
--primary / --primary-foreground→--theme-accent-500 / --theme-accent-on
--muted / --muted-foreground→--surface-subtle / --text-tertiary
--destructive→--ramp-danger-500
--border / --input / --ring→--border-default / --input-border / --border-focus
--radius→--radius-md (6px — shadcn's own internal radius calc)
Why this lives in tokens.css, not a shadcn config file
Because the bridge is plain CSS custom properties on :root, it needs zero shadcn-specific tooling and survives a shadcn component being re-generated, upgraded, or swapped for its Svelte port — see §9C. It's also why light/dark mode and dashboard theming apply to shadcn components automatically: they inherit through the same [data-mode] / [data-theme] cascade as everything else, since --primary is just an alias for a token that already responds to both.
9C

shadcn-svelte — the Svelte port

shadcn-svelte is a community-maintained port of shadcn/ui built for Svelte instead of React, following the same philosophy: components are added to the codebase as owned source files via a CLI, not pulled in as an opaque dependency, and they deliberately preserve the identical CSS variable names shadcn/ui uses. That naming parity is the whole reason a stack change from React to Svelte doesn't cost a second token bridge — tokens.css §6 was written once, against the variable contract, and shadcn-svelte honors the same contract.

AspectBehavior in this stack
InstallationCLI-based, copies component source into the project (typically under a components directory) rather than an npm black box
Styling contractSame CSS variable names as shadcn/ui — no separate H2 Prime token bridge needed for the Svelte port
Underlying primitivesAccessible, unstyled interaction primitives (dialog, popover, combobox, etc.) — accessibility behavior ships with the component, not re-implemented per use
Ownership modelCopied source is local and editable — a component can be adjusted for H2 Prime needs (e.g. the 18px base size, Barlow/Inter family switch) directly, same as any other project file
Ownership means the audit responsibility transfers, too
Because component source is copied in rather than pulled from a versioned dependency, it does not automatically pick up upstream fixes. Any shadcn-svelte component in this project should be checked against §8G and §9E's anti-patterns after generation — most defaults already resolve to token-backed CSS variables, but a generated component occasionally ships an inline Tailwind color utility that should be swapped for the token equivalent before it ships.
9D

Svelte component patterns

Wrapping the semantic HTML patterns from Section 5 in a .svelte file shouldn't change what the rendered markup looks like — the same real elements, the same linked labels, the same ARIA only where necessary. What Svelte adds is props for variants and state, driving which token-backed Tailwind classes apply.

<script lang="ts">
  let {
    variant = "primary",
    disabled = false,
    label,
    ...rest
  }: {
    variant?: "primary" | "secondary" | "ghost" | "danger";
    disabled?: boolean;
    label: string;
  } = $props();

  const variantClass = {
    primary:   "bg-interactive-primary text-interactive-primary-text hover:bg-interactive-primary-hover",
    secondary: "bg-interactive-secondary border border-interactive-secondary-border text-interactive-secondary-text",
    ghost:     "text-interactive-ghost-text hover:bg-interactive-ghost-hover",
    danger:    "bg-feedback-danger-solid text-feedback-danger-on-solid",
  }[variant];
</script>

<button
  type="button"
  class="rounded-btn px-4 py-2 {variantClass}"
  disabled={disabled}
  aria-label={rest["aria-label"] ?? undefined}
  {...rest}
>
  {label}
</button>

Tokens stay global, styles can stay scoped

Svelte's per-component <style> block is scoped to that component by default, but CSS custom properties defined on :root in tokens.css are unaffected by that scoping — var(--surface-raised) resolves identically whether it's read from a Tailwind class or a scoped <style> rule.

Forward ARIA props, don't reinvent them

An icon-only button component should accept and pass through aria-label rather than hardcoding one, so every call site supplies its own accurate label — the same requirement as the plain-HTML pattern in §5H, just expressed as a Svelte prop instead of inline markup.

Semantic elements, not div soup, inside components

A Svelte component for a form field still renders a real <label> linked via for/id, not a styled <div> standing in for one. Componentizing markup is not license to drop the semantics that made it accessible in the first place.

Reactive state maps to existing state tokens

A disabled or error prop should switch to the already-defined --interactive-disabled-* / --input-border-error tokens from Section 8, not a new inline color computed in the component.

9E

Anti-patterns

Don't hand-write a component shadcn-svelte already provides

A custom combobox or dialog reimplemented from scratch re-opens every keyboard-navigation and focus-trap edge case shadcn-svelte's Radix-derived primitives already handle. Generate the shadcn-svelte component and restyle it with tokens instead.

Do restyle through tokens.css §6, not per-component overrides

If a generated shadcn-svelte component looks wrong, the fix is almost always a missing or incorrect mapping in the bridge — not a one-off override added inside that component's copied source.

Don't leave an arbitrary Tailwind value in shipped markup

bg-[#984616] or text-[15px] bypasses the entire token chain — it won't shift with dashboard theming, mode, or a future ADR-driven change the way bg-surface-brand or a semantic type role would.

Do treat a missing token as a Section 8 gap, not a local exception

If no existing token fits, that's a signal to add one to tokens.css (and its @theme entry in main.css) following §8C's naming pattern — consistent with how every other gap in this system has been closed so far.
