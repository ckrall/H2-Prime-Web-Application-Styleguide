H2 Prime Web Application Design System & Guidelines

Section 03 — Typography

The type system for the H2 Prime web application platform. Built for an audience that skews middle-aged to older, is often not tech-savvy, and reads on mobile outdoors as often as at a desk indoors — lawyers, farmers, and local business owners reviewing contracts, permits, and cylinder records. Every size, weight, and family decision below is driven by that audience first, brand character second.

3A

Type scale & semantic roles

Seventeen semantic roles, each bundling family, weight, size, line-height, and letter-spacing as one decision. Component code should reference these roles (--type-h1-* in tokens.css, or the text-h1 / font-display / font-light utilities in Tailwind) rather than raw sizes — the same governance rule already established for color in Section 2. Label and Metric were added alongside the component-role mapping in §3K to cover form/menu/button labels and large KPI values; Modal title was added in the same pass to give dialogs their own heading voice, distinct from H1/H2. A further eight names in §3L are component-scoped aliases onto these seventeen, not new roles in their own right.

Label is deliberately not Overline: Overline is uppercase and tracked for group-level "eyebrow" labeling (table column headers, fieldset legends), while Label is sentence-case and sized for legibility on a single control's own text. Metric intentionally uses Inter bold rather than Barlow Semi Condensed light — a KPI number needs to read as strong and unambiguous at a glance, and light-weight condensed digits lose crispness in outdoor glare. Modal title keeps the Barlow Semi Condensed family for cohesion with the rest of the heading system but switches to weight 400 (never 300) at a one-off 26px that isn't drawn from the raw scale — sitting deliberately between H2's 28px and H3's 22px so a dialog is never mistaken for a page heading. Held to the same 4.5:1 contrast minimum as the font-light roles, even though 400-weight text at this size would qualify for WCAG's 3:1 large-text exception — dialogs are often action-critical (confirm, delete) and this audience shouldn't have to work to read one. See §3K for the component-role mapping that motivated all three additions, and §3L for the aliases layered on top.

3B

Font pairing decision — documented

Architectural decision record — type pairing

Three condensed/display candidates and three body candidates were considered. The winning pairing spends character where it's safe to spend it (large display sizes, where narrowing doesn't cost legibility) and spends safety where the audience needs it most (the much larger surface area of forms, tables, and dense contract data).

3C

Family-switch decision — documented

Architectural decision record — where condensed/light stops

Condensed geometry narrows letterforms, and 300-weight strokes carry less effective contrast than the ratio number suggests — both compound for an older audience reading outdoors. Rather than let weight alone carry the hierarchy at every size, the display family is retired at a fixed threshold and Inter takes over.

Barlow Semi Condensed carries Display, H1, and H2 only — the sizes large enough that narrowing and thin strokes don't cost legibility. H3 and below switch to Inter at 600 weight, which restores full letterform width and a heavier stroke exactly where text gets smaller and reading load goes up.

H2 · 28px
family switch
H3 · 22px
Don't — condensed/light in functional UI

Buttons, nav items, form labels, and table cells never use font-display or font-light, regardless of size. These are high-frequency-read, functional elements where legibility always outranks character.

Do — condensed/light only at Display/H1/H2

Reserve font-display font-light for the three largest heading roles. Everything H3 and smaller — including minor headings — uses Inter at 600 weight for both width and stroke presence.

3D

Base-size decision — documented

Architectural decision record — base size

Tailwind's stock text-base is 16px. H2 Prime's --text-base is deliberately raised to 18px to match an audience that skews older, and every other slot in the generic scale was re-derived from real semantic roles rather than left at Tailwind's defaults.

This is a token-level override, not a one-off style. Any component using the stock text-base utility inherits the larger size automatically. --text-size-md (16px) was added below the new base to keep a step available for secondary and dense text — it did not exist as a distinct role before.

3E

Weight, condensed & contrast rules

Three rules govern every use of the display face, on top of the family-switch boundary in §3C:

Don't rely on the large-text contrast exception

WCAG permits 3:1 contrast for large-scale text. Every font-light role holds 4.5:1 minimum regardless of size — thin strokes lose effective contrast faster than the ratio number suggests, especially in outdoor glare.

Do treat weight-300 as a large-size-only tool

300 weight never appears below the H2 threshold (28px). If a design calls for a light-weight treatment at a smaller size, that's a signal to reconsider the design, not to add a new light-weight role.

Don't use Display outside a true hero moment

Display exists for cover pages and marketing surfaces. It is not bound to any in-app element by default — using it for an ordinary page title inflates the hierarchy and competes with H1.

Do use fluid sizing on Display and H1

Both roles clamp between a mobile-safe minimum and their fixed desktop maximum — see §3G. H2 and below stay fixed; the gap between fixed sizes is already small enough not to need it.

3G

Fluid sizing

Display and H1 are the only two roles that scale with viewport width — both are large enough to feel oversized on a narrow phone screen if left fixed at their desktop size. H2 and everything below stays fixed; the steps are already modest enough not to need it.

Fluid clamp expressions for Display and H1, showing the mobile minimum and desktop maximum each resolves to.
RoleClamp expressionResolves to
Displayclamp(1.75rem, 4vw + 1rem, 2.5rem)28px on narrow mobile → 40px on desktop
H1clamp(1.625rem, 3vw + 1rem, 2.125rem)26px on narrow mobile → 34px on desktop

Treat both expressions as starting points, not final numbers — tune the viewport-width coefficient against real devices once the type system is in the app, and record any change here rather than silently editing tokens.css.

3H

Font loading

Production app — don't use a font CDN at request time

Part of the audience works with unreliable rural connectivity. A stalled Google Fonts request on a weak signal delays first render for exactly the users who can least afford it.

Production app — self-host subsetted variable woff2

Self-host Barlow Semi Condensed, Inter, and JetBrains Mono as variable woff2, subsetted to Latin plus the character set the forms actually need, with font-display: swap.

This documentation site is a different, lower-stakes context — it loads fonts from Google Fonts for convenience (see the @import at the top of h2p-shared.css). Do not treat that as the production pattern.

3J

Anti-patterns

Don't chain four utilities for a heading

A bare <h1>–<h5> already gets the correct family, weight, size, line-height, and tracking from components.css. Reach for text-h1 font-display font-light only when the role is needed on an element that isn't a real heading.

Do use real heading levels in document order

One <h1> per page, no skipped levels. The visual size of a heading is a styling decision — it should never be used to fake the document's actual structure for screen-reader users.

Don't invent a new light-weight role at a smaller size

If a design wants a delicate, editorial feel below 28px, that's a cue to revisit the design against §3C and §3E — not to add a seventeenth role that quietly breaks the contrast policy.

Do flag gaps here instead of improvising silently

This is a start version by design (see the header note in tokens.css §2.17). If a real screen needs a role that doesn't exist yet — a 6th heading level, a new mono role — add it to the token file and this page together, rather than hand-styling a one-off.

3K

Component role mapping

The original fourteen roles in §3A were named for generic document structure (headings, body, caption). Real screens ask for the same decisions at the level of a table cell, a form field, a KPI tile — this section maps those component-level names onto the base scale so nobody re-derives a size from scratch. Three roles didn't exist yet to receive that mapping cleanly, so they were added: Label (sentence-case, semibold, for text that labels a single control), Metric (large, bold, tabular, for standalone KPI values), and Modal title (condensed at a moderate weight, for dialog headings). All three are documented in §3A and live in tokens.css §2.17b. §3L below layers seven more component-scoped names on top — pure aliases, not new roles.

How to read these tables

"Maps to" always names one of the seventeen roles in §3A — never a raw size. Where a role needs a modifier the base role doesn't carry (a color token, tabular-nums), the Notes column says so explicitly. Nothing here is a new size; it's a locked pairing of an existing role to a component context.

3L

Component-scoped type aliases — added 2026-07-16

All seven gaps flagged in §3K are resolved below. Each is a pure alias onto one of the seventeen roles in §3A, with a weight override in two cases — none of them add to that seventeen count. They live in tokens.css §2.17c as their own named custom properties (e.g. --type-toast-body-*), and as .text-* utility classes in components.css, so component code can reference the component's own name instead of every contributor needing to already know which base role it happens to be — the same reasoning already applied to the --radius-btn / --shadow-card aliases in §2.14–§2.15.

Why Currency emphasis isn't Metric

Metric (§3A) is 700-weight, 34px, and reserved for a single standalone KPI value — a stat tile's headline number. Currency emphasis sits inline, inside a table row or a billing line item, next to other text at the same scale; it needs to stand out from a plain number without competing with the page's actual KPI values for visual weight. One alias covers both the billing dashboard and the wage-rate table cells deliberately — if a specific screen later needs more prominence than 600-weight Body small buys, that's a layout or spacing decision, not a cue to bump the font size (§3J).

Modal title — why it isn't an alias

Modal title is deliberately not in the table above, because it isn't an alias — it's documented as its own role in §3A. A dialog needing "definitely distinct from H1/H2" ruled out reusing H3 (Inter, 600, 22px — indistinguishable from any other subsection heading on the page behind it). It kept the Barlow Semi Condensed family for cohesion with the rest of the heading system, but moved to weight 400 — not the 300 used everywhere else Barlow appears — because the extra stroke weight is what makes a smaller, non-fluid 26px size viable without the legibility cost the §3C family-switch ADR warns about. That combination (Barlow + 400 + 26px) exists nowhere else in the scale, which is exactly the point.

3M

Generic tracking & leading scale — added 2026-07-17

Separate from the seventeen semantic roles in §3A, which each pair a fixed line-height and letter-spacing to one specific role, this is the raw generic scale — for ad hoc Tailwind tracking-* / leading-* utility use on elements that aren't one of those seventeen roles. Same relationship the raw spacing and radius scales have to their component-role aliases in Section 4.

Leading scale smoothed 2026-07-17 — --leading-loose changed from 2 to 1.75

The scale originally stepped tight → snug → normal → relaxed at a consistent +0.125, then jumped +0.375 from relaxed to loose — an inherited Tailwind default (2.0) rather than a deliberate H2 Prime value. Lowering loose to 1.75 holds the +0.125 interval across all five stops, the same predictable-progression standard already applied to the spacing and radius scales in Section 4. A dense, professional dashboard product has little real use for true double-spaced text; 1.75 still reads as clearly open relative to normal (1.5) while keeping the scale mathematically consistent. Per-role line-heights in §3A are unaffected — they're independently tuned per role, not sourced from this generic scale.

Both scales are also now available as Figma variables in H2 Prime Design Kit → H2 Prime Typography (tracking/*, leading/*), each with WEB code syntax pointing back to the matching CSS custom property above, so a Figma-side text style and its shipped CSS never drift silently out of sync.
