Design System & Guidelines

H2 Prime Web Application
Design System

A retroactively formalized design system for H2 Prime, an H-2A visa contract management platform serving lawyers, farmers, and local business owners — an audience that skews middle-aged to older, is often not tech-savvy, and works outdoors on a phone as often as at a desk. Built incrementally, one subsystem locked before the next begins, with the rationale for every decision documented alongside it rather than left implicit.

Token correctness pass — 2026-10-25

tokens.css, main.css and components.css were audited end to end and nine defects were fixed, several of them live in production. The two largest: the dark-mode block in tokens.css was an invalid selector list, so dark mode never applied at all; and forty @theme entries in main.css mapped Tailwind namespace names onto themselves, so every radius, shadow, font-weight, leading, tracking, font-display and font-mono utility resolved to nothing. Both were reproduced in a browser before and after. Every change is recorded in the file headers; 175 token pairings across both modes, all three themes and all five phases are now measured and passing.

01
Audience first, brand second
Every size, contrast, and density decision is checked against a non-technical, often outdoor, mobile-first user before it's checked against how it looks.
02
Tokens, never raw values
Components consume semantic tokens only. A hardcoded hex, arbitrary pixel value, or ad-hoc shadow in component code is a bug, not a shortcut.
03
Interactive vs. identity, kept separate
Brand colors (Yellow, Brown) mark who we are. The Neutral ramp marks what you can click. The two roles are never doubled up on the same element.
04
Decisions are documented, not just made
Every non-obvious choice — a hue shift, a contrast override, a rejected alternative — is recorded as an ADR in the relevant section, not left for someone to reverse-engineer later.
05
Semantic HTML, WCAG 2.2 AA minimum
Real elements over generic ones, AA contrast as the floor with AAA where feasible, and color paired with text or shape — never color alone.
06
A start version beats a perfect one
Sections ship as soon as they're internally consistent. Gaps are flagged in anti-patterns sections and closed as real screens surface them.
07
Accessibility is structural
Contrast ratios are verified and focus rings are part of the spec before a component ships — not audited in afterward. Documented alongside each pattern in Section 5, not held in a separate pass.
08
Motion communicates
Transitions signal state and status changes, not decoration. Timing and easing respect an indoor/outdoor viewing environment and never compete with the interface for attention.
09Planned
Writing for experts
Filers and attorneys are seasoned experts; part of the client audience is too, part is new to filing. Copy should sit close to the language clients already meet on government forms, with clear explainers where that gap is real. Balance not yet defined — see Section 12.
10
A surface declares what it is
Every overlay leaves a visible trace of the page it came from, and the direction it arrives from says what kind of surface it is. A thing that covers the whole viewport is not an overlay — it's a page. See Section 14.

Sections

02Complete
Color System
Brand (Yellow + Brown), the consolidated cool Neutral ramp, five utility colors, the Warning anchor decision, and the Neutral-vs-Brown primary-action decision (§2D-2).
02BComplete
Ramp Reference
Full 12-stop technical reference — hex, OKLCH, and contrast ratio — for every ramp in the system.
02CComplete
Ramp Table
Plain hex + OKLCH data table for every ramp, grouped by family — a faster secondary lookup alongside 2B's contrast-ratio reference.
03Complete
Typography
Barlow Semi Condensed + Inter + JetBrains Mono, 18px base, 14-role type scale, family-switch and contrast policy. Two roles added 10-25: overlay title, and the dropped text-5xl slot.
04Complete
Spacing, Layout & Elevation
4px spacing grid, page/content widths and breakpoints, border radius, shadow, and z-index scales.
05Complete
Component Patterns
Buttons, form fields, badges, cards, data tables, and feedback banners — real semantic markup, built on the Neutral-primary decision. Expansion planned: see §5's note on state coverage, form validation, and framework-native versions.
06Complete
Interaction & State Design
Hover, focus, active, disabled, and error states as their own layer: the state model, focus visibility, touch target size, full button and form-field state matrices, selection controls, navigation/tabs, and loading/busy states. A few states (read-only inputs, row selection, loading) are flagged as proposed starting points rather than settled — see §6I. Focus-ring recipe revised 10-25.
07Complete
Motion & Animation
Motion principles, duration and easing tokens, a reduced-motion policy for the outdoor/mobile audience, state-change motion, enter/exit patterns, and anti-patterns. Overlay enter/exit motion is now settled in §14E. See principle 08.
08Complete
Design Tokens
What a token is, the three-tier primitive/semantic/component architecture, naming conventions, light/dark mode mapping, and file structure. Now also carries the --h2p-* naming rule that keeps tokens out of Tailwind's reserved namespaces.
09Complete
Framework Implementation
Tailwind CSS v4, shadcn/ui, shadcn-svelte, and Svelte — how tokens and Section 5's patterns map onto the real stack, so nobody hand-translates raw HTML into components. Overlay-to-shadcn-svelte mapping still to add — see §14I.
10Planned
Contract Phase System
Parked pending a possible approach change — not yet revalidated against Brown/Neutral. See h2prime-ramps-v2.html. Dark-mode phase values were added 10-25 because their absence was a straight bug, not a parked decision; the scheme itself is still open.
11Planned
Dashboard Themes — Client / Filer / Admin
Parked pending a dedicated review pass on per-dashboard Brown/Yellow identity treatment, plus custom/white-label theming and light and dark mode variants for each dashboard. See §2E. Governing rule for this review: theme/accent colors must not sit too close to any utility color (Danger/Warning/Success/Info) — see tokens.css § Dashboard Themes. Includes deciding the still-unresolved "select a color set" theme picker (Purple/Ruby/Lime/Orange swatches), currently held rather than force-mapped since they'd otherwise collide with Violet/Danger/Success/Warning. Dark-mode theme variants were added 10-25 as a defect fix; the identity treatment is untouched.
12Planned
Writing & UX Copy
Filers are seasoned experts; the client audience splits between seasoned and first-time filers. Complements principle 09 — the balance between expert and plain-language copy is not yet defined.
13AComplete
Figma Variable Reference — Global Tokens
Primitives, light/dark semantics, typography, spacing, radius, and elevation mirrored into Figma variable collections, with Code Syntax bindings back to tokens.css. Scoped deliberately to tokens that don't depend on the dashboard theme decision — see §13A-A. Needs a re-sync pass against the 10-25 token revision.
13BPlanned
Figma Variable Reference — Dashboard Themes
Theme-accent, themed navigation, and the still-unresolved color-set picker, mirrored into Figma once Section 11 lands. Depends on §11 — the 13A global mapping doesn't depend on this.
14Complete
Overlay & Surface System
Modal, drawer, sheet, popover, toast and inline expansion as one system, sorted by what each does to the user's sense of place rather than by shape. Settles when a side action is a modal and when it's a panel, the four cues that make a panel legible on a phone, the motion grammar that lets the two mix coherently, nesting rules, and the per-surface accessibility model. Belongs conceptually alongside §05–§07.

Companion documents

Not numbered sections. An amendment records what changed in a section and why; a build record documents the first real application of one, including what it cost. Both are dated, and both are linked from the sections they belong to.

13AAmendment
Figma Variables — 2026-10-25 amendment
Every change made to the Figma variable collections during the token correctness pass: the variables that were missing entirely, the Code Syntax repairs, the new line-height/body-base and Body/base text style, and the corrections fed back into tokens.css. Read alongside Section 13A, which it amends rather than replaces.
NCBuild record
Notification Center — Figma build record
The first application of Section 14 and the first consumer of the 13A variables. Five Figma sections across three roles in both modes, two new local components, and the six things the build turned up — including a live Soft Badge contrast defect reaching every badge in the product, and the drawer width correction that amended Section 14 itself.

What "Re-sync" means on a row above

The section is still correct in substance, but it documents token names or values that changed in the 10-25 correctness pass — the --h2p-* canonical scales, the dark-mode selector form, the revised focus-ring recipe, the corrected --text-on-success and placeholder values, or the retuned viz-2, viz-3 and viz-7. None of them are wrong about a decision; they are out of date about a name or a number. Worth one sweep rather than nine separate edits.
