Section 08 — Design Tokens

8A

What is a design token

A design token is a named value that stands in for a raw design decision — a color, a size, a shadow, a font weight — so that decision can be referenced by name instead of repeated as a literal everywhere it's used. #984616 is a color. --ramp-brown-500 is a token: the same color, but with a name that carries meaning, a single place it's defined, and a single place it changes.

In H2 Prime, tokens are implemented as CSS custom properties (--like-this), defined once in tokens.css and consumed everywhere else — component markup, Tailwind utility classes, and the shadcn/shadcn-svelte component library all read from the same set of names rather than each holding their own copy of a hex code or a pixel value.

Why this matters for H2 Prime specifically
Every rebrand-scale decision this system has already made — retiring Violet as brand, adding Brown, recomputing Neutral to H≈258°, moving the primary action color off Brown and onto Neutral — was a one-file change precisely because components never held raw values. A token layer isn't stylistic preference here; it's what made three separate mid-project pivots cheap instead of a full re-audit of every screen.
8B

Three-tier architecture

Every token in tokens.css belongs to exactly one of three tiers. Each tier only ever points at the tier above it — a semantic token can reference a primitive, but a primitive never references a semantic token, and nothing above Tier 1 contains a raw hex value.

TIER 1
Primitives
Raw ramp values. 12-step OKLCH ramps for every brand and utility color, plus raw scales for spacing, radius, and type size. Never referenced directly in component code.
--ramp-brown-500: #984616;
→
TIER 2
Semantics
Role-named aliases pointing at Tier 1. This is what "light mode" and "dark mode" actually are — the same semantic name resolving to a different primitive depending on [data-mode].
--text-primary: var(--ramp-gray-dark-900);
→
TIER 3
Components
Component-scoped overrides in components.css — applying semantic type roles to real HTML elements, or a single component's one-off need. Still never a raw value.
h1 { font-size: var(--type-h1-size); }
The rule that keeps this from leaking
Component code (Svelte templates, Tailwind classes, shadcn overrides) should only ever reach for Tier 2 or Tier 3 names — bg-surface-page, text-text-primary, rounded-card. A raw --ramp-* reference, or worse a hardcoded hex, inside a .svelte file is a bug to fix, not a shortcut to allow. See §8G.

8C

Token naming conventions

Semantic and component tokens follow a fixed segment order. Not every token uses every segment — --surface-page has no variant or state — but when a segment is present, it always appears in this position.

--interactive-primary-bg-hover
category — the token family (surface, text, border, interactive, feedback, input…)
role — which one within that family (primary, secondary, danger, warning…)
property — which visual property (bg, border, text, icon, solid…)
state — interaction state, only when the token varies by it (hover, active, disabled, error, focus)

Primitive ramps follow a simpler two-segment pattern: --ramp-{name}-{step}, where step is always one of the 12 fixed stops (25 · 50 · 100 · 200 · 300 · 400 · 500 · 600 · 700 · 800 · 900 · 950). Component-scoped tokens in Tier 3 prefer a role-based name over an element name where the role is reusable — --radius-card, not --radius-contract-card — so a new component that is also "card-shaped" can reuse it without a rename.

PatternExampleUsed for
--ramp-{name}-{step}--ramp-neutral-700Tier 1 primitives — every color ramp
--{category}-{role}--surface-raisedTier 2 semantics with no state variation
--{category}-{role}-{property}--feedback-danger-iconTier 2 semantics with multiple visual properties per role
--{category}-{role}-{property}-{state}--interactive-primary-bg-hoverTier 2 semantics that change on interaction
--{role}-{property}--radius-card, --elevation-modalTier 3 component-role aliases (spacing, radius, shadow, z-index)
--type-{role}-{property}--type-h1-leadingSemantic type roles — family, weight, size, leading, tracking bundled per role
One naming exception, and why
--ramp-gray-mid-* and --ramp-gray-dark-* break the pattern deliberately — they're retained as backward-compatible aliases onto the consolidated --ramp-neutral-* ramp (2026-07-13 revision) so existing component-layer references keep resolving without a rename pass. Do not add new references to the legacy names; reach for --ramp-neutral-* or the semantic --neutral-* aliases instead. See tokens.css §1.3.
8D

Light & dark mode mapping

Light mode is the default value of every Tier 2 token, defined directly in :root in tokens.css §2. Dark mode doesn't add new tokens — it redeclares the same semantic names inside a scope that activates two ways at once, so the override applies whether the mode comes from an explicit user/app choice or from the OS-level preference:

[data-mode="dark"],
@media (prefers-color-scheme: dark) {
  :root {
    --surface-page: var(--ramp-gray-dark-950); /* was --ramp-gray-dark-25 in light */
    --text-primary: var(--ramp-gray-dark-25);  /* was --ramp-gray-dark-900 in light */
    /* …every other §2 semantic token redeclared, primitives untouched */
  }
}

Tier 1 primitives never change between modes — --ramp-neutral-700 is the same hex value in both. What changes is which primitive step a Tier 2 name points to: light mode reaches for near-black text on a near-white surface, dark mode inverts to near-white text on a near-black surface, both drawn from the same 12-step ramp.

Light mode

--text-primary on --surface-page

Body copy reads at ~14.5:1 against the page canvas.

--interactive-primary-bg
Dark mode

--text-primary on --surface-page

Same token names, same ramp — the near-white and near-black steps swap roles.

--interactive-primary-bg
Why interactive-primary isn't a simple swap
Most §2 tokens invert cleanly (light step ↔ dark step, same ramp position logic). --interactive-primary-bg does not — it resolves to Neutral-800 in light mode but Neutral-100 in dark mode, both near the opposite end of the ramp from what a naive inversion would suggest, specifically so the fill never goes muddy or vanishes into the dark-mode page canvas. See the primary-action decision documented at the top of tokens.css.

8E

Token file structure

Three files, loaded in a fixed order. Each has one job, and nothing downstream re-defines a token that a file earlier in the chain already owns.

  1. 1tokens.cssAuthoritative source. All three tiers — primitives (§1), light-mode semantics (§2), dark-mode overrides (§3), dashboard theme layer (§4), contract phase context (§5), and the shadcn/Radix bridge (§6). Framework-agnostic — plain CSS custom properties, no Tailwind syntax.
  2. 2main.cssTailwind v4 entry point. Imports Tailwind, imports components.css, and maps every Tier 2/3 token in tokens.css into an @theme block so each one becomes a real Tailwind utility class. Covered in full in Section 9.
  3. 3components.cssTier 3 base layer. Applies semantic type roles to real HTML elements (h1–h6, p, code) inside a Tailwind @layer base block, so correctly-used semantic markup looks right with zero utility classes.

A fourth file, h2p-shared.css, exists only for this documentation site — it is not part of the runtime token system and should never be imported into the product build.

8G

Anti-patterns

Don't reference a Tier 1 primitive from a component

bg-[#984616] or var(--ramp-brown-500) inside a Svelte component skips the semantic layer entirely — it won't respond to a mode change or a future role reassignment the way bg-surface-brand would.

Do add a new semantic token, not a new hardcoded value

If a real screen needs a role that doesn't exist yet, add it to tokens.css §2 (and the dark-mode override in §3) before using it — not as a one-off value in the component that needed it first.

Don't invent a naming pattern mid-file

A token like --btn-primary-color alongside --interactive-primary-bg creates two competing vocabularies for the same concept. Match the segment order in §8C even when it feels verbose for a one-off.

Do keep dark-mode overrides token-for-token complete

Every semantic token declared in §2 needs a considered dark-mode value in §3 — even if that value is "unchanged, see comment" like --border-focus. A silently-missing override falls back to the light-mode value, which usually breaks contrast rather than looking merely undithered.
