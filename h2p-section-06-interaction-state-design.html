6A

The state model

Every interactive element in H2 Prime can carry up to seven distinct states. Not all seven apply to every component — a link has no "disabled," a static card has no "active" — but where a state applies, it draws from the same named layer every time rather than a one-off value invented at the point of use.

StateTriggerToken patternApplies to
DefaultResting state--interactive-*-bg / --input-borderAll interactive elements
HoverPointer over element (no effect on touch)--interactive-*-bg-hover / --input-border-hoverButtons, links, nav items, table rows, inputs
FocusKeyboard focus (or programmatic focus)--border-focus / --input-border-focusEvery focusable element — never optional
Active / pressedMouse down or touch-down, before release--interactive-primary-bg-activeButtons, tabs, toggles
DisabledElement cannot currently be activated--interactive-disabled-*Buttons, inputs, menu items
Error / invalidFailed validation--input-border-errorForm inputs, fieldsets
Selected / currentPARTIALItem is the active tab, current nav page, or a checked table row--nav-item-bg-active / --nav-text-active only — no generic --selected-* layer yetTabs, nav, table row selection, checkbox/radio

Two states are deliberately not layered on top of each other with compounded styling: disabled elements never also show a hover or focus treatment (a disabled control should look and behave like it's off, full stop), and an element that is both selected and hovered shows the hover treatment as a subtle addition to the selected background, not a replacement for it — see the table row demo in §6F.

6B

Focus visibility

Every focusable element gets a visible focus ring — --border-focus, Brand Yellow, 2px, with a small offset so it never merges into the element's own border. This is non-negotiable under WCAG 2.4.7 (Focus Visible) and holds across all three dashboard themes and both light and dark mode, since Yellow's high contrast is the reason it was chosen as the one color that never gets themed away.

Don't use :focus alone

A plain :focus ring also fires on mouse click, which reads as visual noise to someone who didn't ask for it. All H2 Prime focus styling uses :focus-visible, which the browser reserves for keyboard and other non-pointer focus.

Do use :focus-visible everywhere

Every demo on this page uses :focus-visible. It's supported in every browser H2 Prime targets and needs no polyfill.

WCAG 2.2's newer 2.4.11 (Focus Not Obscured, Minimum) also applies: a sticky header, toast, or bottom sheet must never fully cover a focused element. This matters specifically for the mobile bottom-sheet patterns implied by the outdoor/one-handed use case — flagged as an open decision in §6I since no sticky-header/focused-element collision rule is written down yet.

button:focus-visible,
a:focus-visible,
input:focus-visible,
select:focus-visible {
  outline: 2px solid var(--border-focus);
  outline-offset: 2px;
}
6C

Touch target sizeGAP

No file in the system currently sets a minimum tap-target size. This is a real gap, not a minor one — H2 Prime's audience is explicitly older and frequently on a phone outdoors, which is exactly the profile WCAG 2.5.8 (Target Size, Minimum) and the mobile-first principle on the cover page were written for.

Decision point — not yet made
WCAG 2.2 AA's 2.5.8 floor is 24×24 CSS px (with spacing exceptions). Given the stated audience, that floor is arguably too low for H2 Prime's primary actions. The open question is whether to adopt a stricter in-house minimum — 44×44px is the common mobile-platform convention (Apple HIG / Material) — for primary buttons and icon-only controls specifically, while allowing the AA floor for dense contexts like table row actions. This hasn't been decided; treat both numbers below as illustrative until it is.

Note that the current icon button from §5H (9px padding around a 16px icon, 34×34 total) already clears the AA floor but falls short of the 44px convention. Nothing needs to change today — but no new icon-only control should ship smaller than 34×34, and the 44px question should be settled before the pattern multiplies across the mobile client dashboard.

Disabled buttons stay in the tab order — on purpose
H2 Prime uses aria-disabled="true" alongside the native disabled attribute is not the default here: a truly disabled native button is removed from the tab order entirely, which means a keyboard or screen-reader user tabbing through a form has no way to discover why the Submit button won't activate. Where the reason matters (e.g. "Submit contract" disabled until all required fields are complete), prefer a focusable-but-inert pattern (aria-disabled="true" without the native disabled attribute, blocking the click handler in script) so the reason can be surfaced via aria-describedby. Where the reason is obvious or irrelevant (e.g. a "Submitting…" state mid-request), native disabled is fine. This distinction isn't applied consistently across Section 5's examples yet — see §6I.

Decision point — native styling or custom?
Native checkbox/radio rendering is accessible by default but can't be color-matched to the token system (no accent-color token exists either, which is itself a small gap). The open question is whether H2 Prime custom-styles these controls to carry Brand Yellow / Neutral like everything else, or deliberately leaves them native for the reliability that comes with browser-native semantics on an older, less technical audience. Leaning native is reasonable given the audience principle, but it hasn't been written down as a decision — see §6I.
6G

Navigation & tabs

The current page or tab is marked with aria-current="page" (for nav links) or aria-selected="true" (for a tab within a role="tablist") — never by color alone. Both draw from --nav-text-active and --nav-item-bg-active, which already resolve through --theme-accent-* so the active indicator matches whichever dashboard theme (Brown-primary Client/Filer, Violet-primary Admin) is active once Section 11 lands.

Keyboard behavior, not just visual state
A real role="tablist" implementation needs arrow-key navigation between tabs and a single tab stop for the whole group (roving tabindex) per the WAI-ARIA Tabs pattern — that interaction logic lives in the Svelte component, not in this style guide, but it's called out here so it isn't lost between Section 6 (visual state) and Section 9 (framework implementation).

Open questions this section doesn't answer
How long a wait needs a spinner versus a skeleton versus nothing at all; whether a full-page loading state exists and what it looks like; how a failed load is communicated (a distinct state from both loading and empty); and whether aria-live="polite" is the right verbosity everywhere or whether some loads are noisy enough to warrant aria-live="off" with a manual announcement on completion instead. None of this is decided — flagged in §6I.
