H2 Prime Web Application Design System & Guidelines

Section 02 — Color System

The color architecture for the H2 Prime web application platform. Purpose-built for a multi-environment SaaS with three distinct dashboard contexts, five contract phase views, and a full semantic utility palette. Every decision is driven by semantic clarity, perceptual precision, and WCAG 2.2 AA compliance on actual application surfaces.

2A

Ramp structure & palette overview

The palette is built from 11 color ramps. Each ramp is a single hue scaled across 12 stops using OKLCH perceptual color space. OKLCH ensures uniform perceived lightness intervals — equal numeric steps produce equal perceived differences. This makes contrast ratios at specific stops predictable across all ramps.

Stops are numbered 25 · 50 · 100 · 200 · 300 · 400 · 500 · 600 · 700 · 800 · 900 · 950. The extra stops at each end provide more granularity for surfaces (light end) and accessible text on dark surfaces (dark end).

100 – 200UI element backgrounds, hover states on surfacesTable zebra rows, chip fills, hover fills
300 – 400Borders, separators, subtle outlinesCard outlines, dividers, feedback borders
500 – 600Solid fills — buttons, badges, active indicatorsPrimary button, nav active indicator, status badge
700 – 800Accessible text on light surfaces LMFeedback body text, secondary text
900 – 950Deep fills for DM surfaces; maximum contrast textDark mode cards, deepest surface fills

The 11 ramps are organized into four groups:

H2 Prime has two brand colors as of 2026-07-13: a warm golden Yellow and a muted terracotta Brown. Mid Gray and Dark Gray are retired as separate brand anchors — both now draw from a single cool system Neutral ramp (below), which also carries primary interactive surfaces. See §2D-2 for why the primary CTA color is Neutral rather than Brand Yellow or Brown.

2D-2

Primary action color decision — Neutral, not Brown

The single most-repeated interactive color in the product — the primary CTA fill — resolves to the Neutral ramp, not to Brand Yellow, Brown, or the per-theme dashboard accent. This was a close call worth documenting in full, because the initial exploration (see h2prime-ramps-v2.html) proposed Brown for this role.

Brown as primary — rejected

Strength: ties the most-clicked pixel to brand identity; Brown-500 clears AA on white text (6.52:1), Brown-600 clears AAA (9.93:1).

Gap: Brown-500 goes muddy against near-black dark-mode chrome — needs a mode-aware promotion to step 400, so "primary" can't be one ramp step reused across modes.

Conflict: sits only 13.5° from Warning amber in hue — closer than any other pairing in the palette. As primary, this collision risk re-appears on every screen, for an audience that skews older and often views the app outdoors.

Neutral as primary — chosen

Strength: zero hue overlap with any utility ramp, in either mode, permanently. Neutral-600+ clears AAA in light mode; inverted neutral in dark mode has no muddiness failure at any step.

Strength: cleanly separates "who we are" (Yellow + Brown, identity) from "what you can click" (Neutral, interactive) — a more legible model for a non-technical audience.

Gap: the CTA doesn't read as overtly branded on its own — Brown/Yellow must show up deliberately elsewhere in the same view (header bands, icons, illustration) so the brand doesn't disappear from the product surface.

Decision
Go with Neutral. The Warning-hue proximity is a standing, screen-by-screen risk with Brown and a non-issue with Neutral — decisive given the audience (older, non-technical, frequent outdoor/mobile use, where color perception is worse) and the eventual white-label goal, where keeping interactive-primary on a system ramp lowers blast radius when a tenant's brand color doesn't play nicely with the utility ramps. Brown keeps real estate — headers, illustration, badges — just not the button. See tokens.css §2.4 for the resulting token values.

2D

Warning anchor decision — revised 2026-07-13

Architectural decision record — Warning color, revised

The previous decision (per-theme step-600 override to dodge Brand Yellow) is superseded. Warning is now a single conventional amber ramp, anchored at step 500, used identically across Client, Filer, and Admin — the per-theme override and its branching logic are removed entirely.

Familiarity beats hue-purity here. Warning stays a standard amber (H≈55–65°) everywhere. It now sits ~25° from Yellow and ~13.5° from Brown — tighter than the old client-theme override was, and tighter to Brown (used everywhere, unrestricted) than to Yellow (the one color already kept fully out of status roles). This is exactly why Brown was rejected as the primary interactive color rather than Warning being pushed again — see §2D-2.

Rejected — push Warning again

Chasing more hue separation from Brown would mean a third Warning variant (after the original amber, then the client-theme step-600 orange-amber) with no natural resting hue left — Danger already holds H≈15°, and pushing further toward red risks Warning reading as Danger instead.

Chosen — hold the line on lightness/chroma

Warning-500 is bright and saturated (a true safety-amber); Brown-500 is muted and dark (a terracotta identity color). The 13.5° hue gap holds up in practice because these two colors don't actually look alike side by side — managed by usage governance (Brown and Yellow both stay out of status/feedback roles) rather than by hunting for more hue distance.

Admin / Help violet overlap

The Admin accent (Violet, H≈280°) and the Help utility color (H≈280°) share the same hue family. They are distinguished by role — Admin violet appears on interactive surfaces (buttons, nav active indicators). Help violet appears on passive feedback surfaces (banners, badges). In any Admin view where both appear, they must always be accompanied by a text label; never distinguish them by color alone.

Semantic token rules of use

The token system has three tiers. Understanding which tier a token belongs to determines where it may be used.

TierVariable prefixWho uses itExample
1 — Primitives--ramp-*tokens.css only--ramp-yellow-500
2 — Semantics--feedback-*, --surface-*, --text-*, --interactive-*, --theme-*Component tokens & theme blocks in tokens.css--feedback-warning-solid
3 — Tailwind utilities--color-* (in main.css @theme)Component JSX/HTML via Tailwind classesbg-feedback-warning-solid
Never

Reference --ramp-* primitives directly in component files. bg-[#FFC20E] or style="background:var(--ramp-yellow-500)" in a component bypasses the token layer. Theme switching and dark mode breaks.

Use utility colors decoratively. A violet card border that doesn't mean "help" trains users to ignore Help banners.

Hard-code hex values in JSX for any color covered by the token system.

Always

Reference semantic tokens via Tailwind classes: bg-feedback-danger, text-feedback-danger-text, border-feedback-danger-border.

Use phase tokens via the [data-phase] attribute on a container rather than directly in component styles.

Change the token alias in tokens.css when a color decision changes — never refactor component files for a color update.

2L

Anti-patterns

Using Yellow as Warning

Brand Yellow (#FFC20E) must never be used for Warning states even though it visually resembles a caution color. Its primary identity is the H2 Prime brand interactive color. Any yellow warning badge, alert, or state will read as "H2 Prime branded" — not "caution."

Using utility colors decoratively

Never apply Danger red, Success green, Info blue, or Help violet as accent colors, card borders, or illustrative fills outside of their semantic context. Users learn to read these hues as signals — decorative use trains them to ignore real alerts.

Hue-only phase or state distinction

Phase 3 (burnt orange) and Danger (red-orange) are 13° apart. Phase 4 (fuchsia) and Help (violet) are 12° apart. Never rely on hue alone to distinguish these. Always pair with a text label. Consider shape or icon cues for critical states.

Using ramp primitives in components

Never reference --ramp-yellow-500, bg-[#FFC20E], or any raw hex in component files. All components must consume semantic tokens only. If a semantic token doesn't exist for your use case, add one to tokens.css.

Warning step 500 in client theme

In the client dashboard, the warning semantic tokens intentionally resolve to step 600 (H≈38°) — not step 500. Never override this back to step 500 in client-theme component styles. The one-stop shift is the collision-avoidance mechanism. See §2D.

Admin violet for Help in admin view

The Admin accent (violet interactive) and Help utility (violet passive) share a hue family. Never style a Help banner using accent violet tokens, or style an interactive element using Help tokens. The distinction is role-based: interactive vs. passive feedback.
