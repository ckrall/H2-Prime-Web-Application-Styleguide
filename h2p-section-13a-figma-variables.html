Section 13A — Figma Variable Reference — Global Tokens

How the mode-independent parts of tokens.css — primitive ramps, light/dark semantics, typography, spacing, radius, and elevation — are mirrored into Figma variable collections, and how each variable's Code Syntax field is kept pointed at the matching CSS custom property so a Figma value and its shipped code can't silently drift apart. This section is numbered 13A rather than 13 because it's a deliberate split: it covers only tokens that don't depend on the still-unresolved dashboard theme decision. The theme-dependent half is Section 13B, once Section 11 lands — see §13A-A.

13A-A

Scope — 13A vs. 13B

Section 13 was originally scoped as one pass covering "light mode, dark mode, and per-dashboard theme variables," and parked entirely because the dashboard theme review (§11) hadn't happened. That blocked more than it needed to: the global token layer — primitives, light/dark semantics, type, spacing, radius, elevation — is already locked and hasn't changed since the Neutral/Brown revision. Only the dashboard theme accent layer (§4 in tokens.css) is genuinely unresolved. So the section splits in two:

13A — Starts now
Global tokens
Every primitive ramp, both semantic modes, typography, spacing, radius, and elevation. Nothing here depends on how Client/Filer/Admin themes resolve — the reverse is true, per §13A-B.
→
13B — Blocked on §11
Dashboard theme variables
--theme-accent-*, themed navigation (--nav-*), and the still-unresolved "select a color set" picker. Consumes 13A's Primitives collection by reference once the per-dashboard identity treatment is decided.
Why this split is safe
Every --theme-accent-* value in tokens.css §4 is an alias onto a primitive ramp already defined in §1 (Yellow, Sky Blue, Violet). The primitive ramps themselves aren't in question — Sky Blue and Violet are already fully specified 12-step ramps, they're just not yet assigned to a settled role. 13A mirrors the ramps as-is; 13B only has to decide which alias points where and add that thin mapping layer on top. Nothing built in 13A gets thrown away when §11 resolves.
A third thing that's also out of scope here
Contract Phase colors (tokens.css §1.11 primitives, §2.13 semantic aliases) are not part of either 13A or 13B — they're tied to Section 10 (Contract Phase System), which predates the Brown/Neutral revision and hasn't been revalidated. They'll get their own pass once §10 resolves, most likely alongside 13B rather than a separate 13C, but that's not decided yet.
13A-B

Variable architecture

Figma's Collections + Modes model maps onto the existing CSS three-tier system directly enough that no new mental model is needed — a Figma collection is a tier, and a Figma mode is what [data-mode] already does in CSS.

H2 Prime / Primitives
1 mode — Default
Mirrors tokens.css §1. Every ramp, every step, raw color values. Never bound directly to a layer fill in product screens — only referenced by the Semantic collection.
H2 Prime / Semantic
2 modes — Light, Dark
Mirrors tokens.css §2–§3. Every variable aliases a Primitives variable; the alias target changes per mode, exactly like the [data-mode="dark"] override block.
H2 Prime / Typography
1 mode — Default
Already live (see §3's typography section). tracking/* and leading/* as number variables, referenced inside Figma Text Styles rather than driving type directly — see §13A-E.
H2 Prime / Layout
1 mode — Default
New in this pass. space/* and radius/* as number variables. Elevation ships as Figma Effect Styles, not variables — see §13A-E for why.
H2 Prime / Theme13B
3 modes — Client, Filer, Admin
Not created yet. Will alias into Primitives once §11 resolves which ramp each dashboard's accent, nav, and interactive-secondary treatment actually uses.

Every Figma variable name uses forward slashes as the Figma-native group separator, mapped one-to-one from the CSS token's hyphenated segments — --ramp-neutral-700 becomes neutral/700 inside the Primitives collection, --text-secondary becomes text/secondary inside Semantic. This keeps the segment order from §8C intact; only the delimiter changes.

interactive/primary/bg is a real exception, not a mapping error
Most Semantic variables mirror the same ramp step in both modes with the "which end is light/dark" logic flipped. interactive/primary/bg doesn't — it's Neutral-800 in Light and Neutral-100 in Dark, both near-opposite ends deliberately, so the fill never goes muddy or vanishes into the dark canvas. Anyone editing this variable in Figma should see both alias targets and not "correct" the dark value to Neutral-900 by pattern-matching the rest of the collection. Same logic as the callout in §8D — restated here because it's the row most likely to get silently "fixed" by someone working ramp-by-ramp in Figma without the CSS-side rationale in view.
Data visualization uses one mode on purpose
--viz-* tokens (chart series, tooltip, grid line) stay visually dark-surfaced regardless of app mode — a light-mode dashboard still renders chart tooltips on a dark chip, matching most charting-library conventions. The Figma viz/* group should be added to the Semantic collection but pinned to a single value per variable rather than given Light/Dark mode values, or Figma will silently invent a "light mode" tooltip variant that has no CSS equivalent to ship.
13A-E

Typography & Layout collections

Not every token in tokens.css §2.14–§2.19 maps to a Figma variable cleanly — Figma variables cover color, number, string, and boolean, but a full type role (family + weight + size + line-height together) is better represented as a Figma Text Style that references number variables, not as one variable itself.

tokens.css sourceFigma representationRationale
§2.17 Typography — family, weight, sizeText Styles (not variables)Figma Text Styles are the native unit designers apply to text layers; a bare number/string variable for font size still requires a style to actually use it on a text node.
§2.17 Typography — tracking, leadingtracking/*, leading/* number variablesAlready live per §3's note — these plug into the Text Styles above so a tracking change propagates from one number variable instead of a per-style edit.
§2.16 Spacingspace/* number variablesBind directly to auto-layout gap/padding in components — the most direct variable-to-property match in the whole system.
§2.15 Border radiusradius/* number variablesBind directly to corner radius on frames/shapes.
§2.14 Elevation / shadowsEffect Styles (not variables)Figma shadows are multi-property effects (offset, blur, spread, color, opacity) — Effect Styles are the correct native unit, same reasoning as Text Styles above.
§2.18 Z-indexNot mirroredOUT OF SCOPENo design-time visual meaning — layer order in Figma is manual and z-index is a dev-only stacking concern. Documented in code only.
§2.19 Motion (duration/easing)Not mirroredOUT OF SCOPEFigma prototyping transitions aren't driven by these variables and smart-animate easing curves don't map 1:1 onto CSS cubic-beziers. Section 7 stays the source of truth; a Figma-side reference would need its own drift-check most designers can't verify visually.
13A-F

Code Syntax binding

Every Figma variable in scope for 13A gets its Code Syntax field (Web platform) set to the exact CSS custom property name it mirrors. This is what keeps a Figma value and its shipped CSS from drifting silently apart the way the stale hex comments in tokens.css did before this cleanup pass — the binding is machine-checkable, not just a naming convention someone has to remember to keep in sync.

// Figma variable: neutral/700  (Primitives collection)
// Code Syntax → Web: --ramp-neutral-700

// Figma variable: text/secondary  (Semantic collection, Light mode)
// Code Syntax → Web: --text-secondary
// Value: alias → neutral/700

Do treat a Code Syntax mismatch as a bug report
If a Figma variable's Code Syntax field and its actual behavior in the shipped app disagree, that's a signal one side is stale — same category of issue as the hex-comment cleanup earlier in this pass — and should get fixed at the source (usually tokens.css, since it's authoritative) rather than quietly edited in Figma to match what the screen currently looks like.
13A-G

Gaps & open decisions

Not yet done

The Semantic collection's Dark mode values need a full pass to alias every row against the corrected §13A-D table — this section documents the intended mapping, it doesn't confirm every existing Figma variable already matches it. Treat §13A-D as the spec to audit against, not a confirmation that Figma is already correct.

Ready to build on

Primitives, Typography (partially live already), and Layout collections have no open dependencies — a designer can start binding component variants to these today without waiting on §10 or §11.

Deliberately deferred

Theme collection (13B), Contract Phase primitives/semantics, and themed Navigation tokens — all covered in §13A-A. Don't create placeholder Figma variables for these ahead of time; an empty or guessed alias is worse than an absent one, since it looks decided when it isn't.

Worth deciding next

Whether Contract Phase (currently unassigned to either 13A or 13B) gets folded into 13B once both Section 10 and Section 11 resolve, or stays a separate 13C. No need to decide now — noted here so it isn't forgotten when §10/§11 land.
